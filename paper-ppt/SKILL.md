# paper-ppt：AI 理解、AI 设计、AI 看图迭代

目标：产出一份**准确、可讲、视觉专业、可编辑、可复核**的学术汇报。

基本分工：

- **AI**：理解论文、选择证据、组织叙事、设计页面、看图审阅、决定如何修改；
- **代码**：读取/绘制/渲染/记录/检查，不替代内容与视觉判断。

不要构建“文本 → 固定布局 → 自动填充”的模板流水线，也不要用程序规则给页面机械打分代替视觉模型。

## 0. 开始前

读取已有信息：

- 论文 PDF / Markdown；
- 风格参考：风格名、文字描述、截图、图片、网页 slide 均可；
- 用户已有 PPT（如果有）；
- 时长、听众、语言和其他明确要求。

**风格参考不要求提供 PPTX，也不是固定模板资产。**

用户没有给出完整条件时，采用可逆默认值并写入 `design-brief.md`，不要为非关键偏好频繁打断任务。

同时确认当前环境是否具备：

- 文本/PDF 读取；
- 原始 PDF 页面或图片查看；
- PPT 创建/编辑；
- PPT 渲染；
- 真实图像输入能力。

有独立视觉审阅 Agent 就使用；否则由具备图像输入能力的主 Agent 分阶段完成设计与自审，并明确标记 `self-review`。

没有视觉能力时，可以输出内容/结构草案，但不能声称视觉已经验收。

## 1. Source：先理解论文，再选素材

先通读论文，形成研究主线，再决定哪些内容值得进入汇报。

Markdown 用于理解正文，**原 PDF 页面是 Figure、Table 和公式的视觉真值**。每张准备进入 PPT 的图表都要实际查看。

视觉检查至少确认：

- Figure/Table 编号和 caption；
- 子图对应关系；
- 坐标轴、单位、图例和指标方向；
- 裁切是否完整；
- 页面缩小时文字是否还能读；
- 图能支持什么结论、不能支持什么结论。

产出 `source-notes.md`，记录：

- 论文版本与来源；
- 章节/页码；
- 关键图表；
- 重要数字与实验条件；
- 仍未确认的内容。

明确区分：

1. 作者原文结论；
2. 可核验计算；
3. 汇报者解释；
4. 延伸设想。

未确认数字不要进入正式页面。

## 2. Design：先决定怎么讲，再决定怎么画

阅读：

- [talk-structure.md](references/talk-structure.md)
- [style-guide.md](references/style-guide.md)
- [Academic Clean](references/academic-clean.md) 或 [Academic Rich](references/academic-rich.md)

默认路由：

- 组会 / 精读 / 答辩 / 简洁正式 → **Academic Clean**
- 课程展示 / 公开分享 / 更强演示感 → **Academic Rich**
- 不确定 → **Academic Clean**

用户明确指定风格时优先遵循用户要求。

风格参考可以只有文字；如果用户提供截图、图片或网页 slide，视觉 AI 必须实际查看，只提炼：

- 层级；
- 网格；
- 留白；
- 密度；
- 配色；
- 图文关系；
- 页面节奏。

**不要复制具体坐标、占位符、品牌标识或整页结构。**

填写 [design-brief.md](references/design-brief.md)，再生成 `storyboard.md`。每页至少明确：

- 本页要回答的问题；
- 听众应记住的结论；
- 证据来源；
- 不得改错的术语/数字；
- 视觉焦点与阅读顺序；
- 哪些内容不放这页；
- 演讲备注目标；
- 预计时长；
- 可读性风险。

storyboard 是创作说明，不是程序布局输入。

## 3. Pilot：先验证方法页和实验页

不要先做完整 deck。

优先制作：

1. 一页方法/机制页；
2. 一页实验/结果页；
3. 篇幅足够时再加封面。

这两类页面最能暴露设计是否真的适合论文。

AI 自主构图，可以使用宿主演示工具，也可以编写当次 PptxGenJS 绘制代码。低层 helper 只减少重复劳动，不决定页面长什么样。

制作后立即：

```text
生成 → 渲染 → 看图 → 指出具体问题 → 修改 → 再渲染
```

样页通过后再扩展到全稿。样页确认的是**视觉语言**，不是要求后续页面复制同一布局。

## 4. Slides：1–3 页一批生成与复审

每批 1–3 页。

要求：

- 标题、正文、来源和必要标注保持可编辑；
- 论文原图可以作为图片；
- 自绘解释图优先使用可编辑形状/矢量；
- 生成式图片只能用于非证据性的概念/气氛素材；
- 禁止生成实验结果、补画论文数据或伪造系统截图。

每页写正式口语演讲备注。复杂 Figure 先告诉听众“怎么看”，再解释机制或结果。

每批都走：

```text
制作
→ 渲染
→ 视觉模型实际看每一页
→ 对照论文证据与设计简报
→ 局部修改
→ 重新渲染
→ 复审
```

审阅问题要具体到：**页码 / 区域 / 严重程度 / 为什么影响理解 / 应如何修改**。

同一页连续多轮小修仍没有改善时，优先改变表达方式，例如：

- 拆页；
- 放大局部；
- 删除次要信息；
- 改用流程/对比/逐步聚焦。

不要无限微调几像素。

## 5. Review：内容与视觉分开终审

### 内容终审

核对页面和演讲备注中的：

- 关键结论；
- 数字；
- baseline；
- 实验条件；
- 指标方向；
- 因果表述；
- 专有名词；
- 局限与推测。

页面克制不代表口播可以夸大。

### 视觉终审

查看：

1. 最终版本所有全尺寸页面；
2. contact sheet / 缩略图总览。

全尺寸页面用于看文字、图例、裁切和标注；总览用于看整套节奏、密度和一致性。两者不能互相替代。

任何影响页面像素的修改都会使旧视觉结论失效。全局字体、主题或页码改动后，应重新渲染受影响范围。

视觉审阅记录遵循 [visual-review.md](references/visual-review.md)。

## 6. 交付

建议交付：

- `deck.pptx`
- `speaker-notes.md`
- `contact-sheet.png`
- `qa-summary.md`

工作目录中保留：

- 原始论文；
- Markdown / 图片素材；
- `source-notes.md`
- `design-brief.md`
- `storyboard.md`
- 生成源；
- 每轮渲染结果；
- `review-log.json`

这样后续可以做增量修改，而不是从头重做。

`qa-summary.md` 应明确写出：

- 事实检查情况；
- 视觉审阅方式；
- 最终审阅版本；
- 使用的渲染器；
- 是否在目标 PowerPoint 环境实际打开；
- 仍未解决的问题。

没有验证过的项目就写“未验证”，不要用“全部通过”掩盖缺口。

## 7. 增量修改原则

用户说“不要重做”时：

- 锁定未涉及页面；
- 只修改指定范围；
- 重新渲染修改页及受影响邻页；
- 重新做对应视觉检查；
- 不把一次小改动扩展成整套重构。
