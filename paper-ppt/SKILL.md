# paper-ppt：AI 理解、AI 设计、AI 看图迭代

目标：产出一份**准确、可讲、视觉专业、可编辑、可复核**的学术汇报。

基本分工：

- **AI**：理解论文、选择证据、组织叙事、设计页面、看图审阅、决定如何修改；
- **代码**：读取/绘制/渲染/记录/检查，不替代内容与视觉判断。

不要构建“文本 → 固定布局 → 自动填充”的模板流水线，也不要用程序规则给页面机械打分代替视觉模型。

## 0. 开始前

读取已有信息：

- 论文 PDF / Markdown；
- 风格参考：风格名、文字描述、截图、图片、网页 slide 均可；
- 用户已有 PPT（如果有）；
- 时长、听众、语言和其他明确要求。

**风格参考不要求提供 PPTX，也不是固定模板资产。**

用户没有给出完整条件时，采用可逆默认值并写入 `design-brief.md`，不要为非关键偏好频繁打断任务。

**详略程度是关键条件，不是非关键偏好。** 用户没说时长、页数或“详细/简略”时，开工前用一句话问一次，并给出默认选项让用户一个词就能答，例如：

> 这篇要讲多细？简略版约 10 页、8–10 分钟，只讲主线和关键结果；详细版约 18–20 页、15–20 分钟，含测量/方法分解和主要实验。不说的话我按详细版做。

- 用户已给时长或页数 → 直接推断详略，不再问；
- 用户明确说“你看着办 / 不用问” → 按详细版，写入 `design-brief.md`；
- 只问这一次，和其他必要问题合并成一条消息；
- 各档位的页数、内容范围和备份页策略见 [source-sufficiency.md](references/source-sufficiency.md) §1。

同时确认当前环境是否具备：

- 文本/PDF 读取；
- 原始 PDF 页面或图片查看；
- PPT 创建/编辑；
- PPT 渲染；
- 真实图像输入能力。

有独立视觉审阅 Agent 就使用；否则由具备图像输入能力的主 Agent 分阶段完成设计与自审，并明确标记 `self-review`。

没有视觉能力时，可以输出内容/结构草案，但不能声称视觉已经验收。

## 1. Source：先理解论文，再选素材

### 1.1 获取素材：两条并列可选路径

| 路径 | 做法 | 何时用 |
| --- | --- | --- |
| **A. 原生** | 智能体自己截图 + 视觉识别：`paper-extract/scripts/pdf_snap.py` 的 `pages` / `text` / `inventory` / `crop` | 宿主能看图、PDF 有文本层（默认） |
| **B. MinerU** | [paper-extract](../paper-extract/SKILL.md) 的 MinerU 路径 → Markdown | 扫描件、公式要 LaTeX、表格多、要可复用 Markdown、宿主不能看图 |

两者可以并行：B 出正文，A 出截图与原图裁切。无论哪条路径，**原 PDF 页面都是 Figure、Table 和公式的视觉真值**。使用的路径写入 `source-notes.md`。

### 1.2 理解与选材

先通读论文，形成研究主线，再决定哪些内容值得进入汇报。

文本（宿主读取、`pdf_snap.py text` 或 MinerU Markdown）用于理解正文，每张准备进入 PPT 的图表都要实际查看页面截图或裁切图。

视觉检查至少确认：

- Figure/Table 编号和 caption；
- 子图对应关系；
- 坐标轴、单位、图例和指标方向；
- 裁切是否完整；
- 页面缩小时文字是否还能读；
- 图能支持什么结论、不能支持什么结论。

产出 `source-notes.md`，记录：

- 论文版本与来源；
- 章节/页码；
- 关键图表；
- 重要数字与实验条件；
- 仍未确认的内容。

明确区分：

1. 作者原文结论；
2. 可核验计算；
3. 汇报者解释；
4. 延伸设想。

未确认数字不要进入正式页面。

### 1.3 内容充足性自检

进入 Design 前，由 AI 自主判断素材够不够支撑所选详略档位，按 [source-sufficiency.md](references/source-sufficiency.md) §2 逐项检查：图表清单覆盖、关键数字可溯源、摘要主张有证据、方法讲得通、文本层可信度。

- 不足但能自己补：回到页面截图、附录、补充材料、项目主页或代码仓库补齐；
- 补不齐：写进 `source-notes.md` 的“未确认”，相关页面不放该数字或改为定性表述；
- 只有用户知道的（汇报重点、听众背景、组里关心的问题）：问用户，最多一次；
- 路径 A 不够用（扫描件、公式/表格过多、视觉识别不可靠）：建议切换或叠加路径 B。

自检结论（够 / 不够、补了什么、还缺什么）写入 `source-notes.md` 末尾。

## 2. Design：先决定怎么讲，再决定怎么画

阅读：

- [talk-structure.md](references/talk-structure.md)
- [style-guide.md](references/style-guide.md)
- [Academic Clean](references/academic-clean.md) 或 [Academic Rich](references/academic-rich.md)
- [slide-style-gallery.md](references/slide-style-gallery.md)：从真实顶会/组会 deck 蒸馏的 11 条版式手法，以及海外 / 国内组会两种风格方言

默认路由：

- 组会 / 精读 / 答辩 / 简洁正式 → **Academic Clean**
- 课程展示 / 公开分享 / 更强演示感 → **Academic Rich**
- 不确定 → **Academic Clean**

风格方言（与上面的视觉语言叠加使用，见 [slide-style-gallery.md](references/slide-style-gallery.md) §2–§3）：

- 英文汇报 / 海外组会 / reading group → **International**：白底、标题即结论、增量构建、研究问题编号导航；
- 中文组会 / 国内学术报告 → **Domestic**：提纲页、“一、二、三”标题前缀、标题关键词强调、出处标签、结尾讨论问题；
- 用户未说明时，按汇报语言选择：中文 → Domestic，英文 → International。

场景更具体时，从另外 7 套预设中选（依据：105 套真实 deck 的蒸馏，见 [slide-style-atlas.md](references/slide-style-atlas.md) §4 速查表）：

| 预设 | 场景 |
|---|---|
| `keynote-minimal` | 白底极简发布会式：英文 talk、job talk、导师偏好简洁 |
| `systems-talk` | 系统 / 网络 / 存储 / 数据库论文：贡献追踪条、Insight 卡、比值结果 |
| `theory-beamer` | 理论 / 算法 / 数学：Metropolis 式、定理色块、一个符号一种颜色 |
| `dark-tech` | 工业分享、技术沙龙：深色底、focus-dim |
| `editorial` | HCI / 可视化 / 图形学 / 科普：衬线、插画为主 |
| `defense-cn` | 国内答辩、开题、中期、基金汇报：校色标题带、章节导航、创新点卡片 |
| `jp-gothic` | 日文 / 韩文报告，或日系高密度论文分享 |

只选一套；不确定就用方言默认的 Domestic / International。选定方言/预设写入 `design-brief.md`。

所有方言和预设都可直接调用（[styles/](styles/README.md)）：`tokens.json` 定义字体、字号、配色语义和网格，`assets/style-presets.js` 提供封面、提纲/问题导航、章节、方法、增量构建、公式讲解、结果、总结等页面原型。使用预设时：

- storyboard 中为每页标注原型名；没有合适原型的页面自由绘制，但仍遵守该预设的 token 与硬性约束（见对应 `STYLE.md` §5）；
- 先看 `styles/<name>/refs/` 中的真实参考页和 `samples/` 中的示例页，再动手；
- 预设是起点：渲染后按看图结论改坐标、换原型或拆页，不要为了套原型牺牲论文表达。

用户明确指定风格时优先遵循用户要求。

风格参考可以只有文字；如果用户提供截图、图片或网页 slide，视觉 AI 必须实际查看，只提炼：

- 层级；
- 网格；
- 留白；
- 密度；
- 配色；
- 图文关系；
- 页面节奏。

**不要复制具体坐标、占位符、品牌标识或整页结构。**

填写 [design-brief.md](references/design-brief.md)，再生成 `storyboard.md`。每页至少明确：

- 本页要回答的问题；
- 听众应记住的结论；
- 证据来源；
- 不得改错的术语/数字；
- 视觉焦点与阅读顺序；
- 哪些内容不放这页；
- 演讲备注目标；
- 预计时长；
- 可读性风险。

storyboard 是创作说明，不是程序布局输入。

## 3. Pilot：先验证方法页和实验页

不要先做完整 deck。

优先制作：

1. 一页方法/机制页；
2. 一页实验/结果页；
3. 篇幅足够时再加封面。

这两类页面最能暴露设计是否真的适合论文。

AI 自主构图，可以使用宿主演示工具，也可以编写当次 PptxGenJS 绘制代码。低层 helper 只减少重复劳动，不决定页面长什么样。

制作后立即：

```text
生成 → 渲染 → 看图 → 指出具体问题 → 修改 → 再渲染
```

样页通过后再扩展到全稿。样页确认的是**视觉语言**，不是要求后续页面复制同一布局。

## 4. Slides：1–3 页一批生成与复审

每批 1–3 页。

要求：

- 标题、正文、来源和必要标注保持可编辑；
- 论文原图可以作为图片；
- 自绘解释图优先使用可编辑形状/矢量；
- 生成式图片只能用于非证据性的概念/气氛素材；
- 禁止生成实验结果、补画论文数据或伪造系统截图。

每页写正式口语演讲备注。复杂 Figure 先告诉听众“怎么看”，再解释机制或结果。

每批都走：

```text
制作
→ 渲染
→ 视觉模型实际看每一页
→ 对照论文证据与设计简报
→ 局部修改
→ 重新渲染
→ 复审
```

审阅问题要具体到：**页码 / 区域 / 严重程度 / 为什么影响理解 / 应如何修改**。

同一页连续多轮小修仍没有改善时，优先改变表达方式，例如：

- 拆页；
- 放大局部；
- 删除次要信息；
- 改用流程/对比/逐步聚焦。

不要无限微调几像素。

## 5. Review：内容与视觉分开终审

### 内容终审

核对页面和演讲备注中的：

- 关键结论；
- 数字；
- baseline；
- 实验条件；
- 指标方向；
- 因果表述；
- 专有名词；
- 局限与推测。

页面克制不代表口播可以夸大。

### 视觉终审

查看：

1. 最终版本所有全尺寸页面；
2. contact sheet / 缩略图总览。

全尺寸页面用于看文字、图例、裁切和标注；总览用于看整套节奏、密度和一致性。两者不能互相替代。

任何影响页面像素的修改都会使旧视觉结论失效。全局字体、主题或页码改动后，应重新渲染受影响范围。

视觉审阅记录遵循 [visual-review.md](references/visual-review.md)。

## 6. 交付

建议交付：

- `deck.pptx`
- `speaker-notes.md`
- `contact-sheet.png`
- `qa-summary.md`

工作目录中保留：

- 原始论文；
- Markdown / 图片素材；
- `source-notes.md`
- `design-brief.md`
- `storyboard.md`
- 生成源；
- 每轮渲染结果；
- `review-log.json`

这样后续可以做增量修改，而不是从头重做。

`qa-summary.md` 应明确写出：

- 事实检查情况；
- 视觉审阅方式；
- 最终审阅版本；
- 使用的渲染器；
- 是否在目标 PowerPoint 环境实际打开；
- 仍未解决的问题。

没有验证过的项目就写“未验证”，不要用“全部通过”掩盖缺口。

## 7. 增量修改原则

用户说“不要重做”时：

- 锁定未涉及页面；
- 只修改指定范围；
- 重新渲染修改页及受影响邻页；
- 重新做对应视觉检查；
- 不把一次小改动扩展成整套重构。
