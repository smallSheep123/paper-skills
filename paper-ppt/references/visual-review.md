# 视觉 AI 审阅协议

## 接入真实模型，而不是假定工具存在

先用宿主的工具发现机制确认能否查看图片、调用视觉模型/子 Agent、编辑 PPT、渲染页面。工具名由宿主决定，本文件不要求某家模型或某个插件。

优先独立的视觉审阅 Agent；否则由具备实际图像输入能力的主 Agent 执行，并记录 `self-review`。纯文本模型读文件名、替代文字、图片尺寸或 XML 不算看图。只有发送了实际图像且取得审阅输出，才能生成视觉审阅记录。不能自动联网上传论文到第三方服务；遵守用户/宿主的数据权限。

每次视觉调用提供：实际图片、相关原论文页面、当次设计简报、该页目标和需要核对的证据。不要把“这是故意留白”“学术风所以字小”写成免检理由；设计意图只是背景，审阅者仍可否决。不要让生成者仅靠代码自行宣布通过。

## 五阶段与具体审阅提示

**source：原始证据**

> 查看这些原论文页面和提取图片。识别图号、子图、图注、轴、单位、图例、指标方向和条件。指出错配、裁切或不可读之处。只根据实际可见信息与给定正文解释，不补全看不清的值；说明这张图能支持和不能支持的结论。

**design：视觉定调**

> 查看用户参考图（若有）和当前设计样页。提炼视觉层级、密度、字体、色彩、对齐和图文组织，判断是否适合本次论文与听众。没有参考图时只评价实际样页，不声称参考过不存在的文件。给出需保留与需改变的设计原则。

**pilot：代表性样页**

> 查看方法页与实验页的真实渲染图，并对照原论文。能否沿页面讲清机制？图表条件是否足够？正文和图例在正常显示尺寸下能否读清？指出具体区域和修改动作，不因没有溢出就通过。

**slides：逐页审阅**

> 查看这一批每一页的全尺寸渲染图。依次检查内容忠实、图像/公式完整、讲述顺序、文字与图例可读、对齐间距、视觉焦点、术语和配色的一致性。记录每个问题所在页与区域、严重程度、影响和修复建议。修复后重新看图。

**deck：终审**

> 查看最终版本所有页面和总览图。确认逐页问题已解决，整套节奏、密度与设计统一，不存在从清楚样页退化为截图堆积的页面。全尺寸审阅不可被总览缩略图替代。对未看过或版本变化的图片不得确认通过。

## 记录格式

工作目录保存 `review-log.json`。下面是**结构示意，不是已经发生的模型调用**；不可复制示例占位符作为通过证据。路径相对日志所在目录，实际图片必须存在。`inputs` 可同时记录本页与对照原图。`source`/`design`/`pilot` 按阶段记录；`slides` 按页记录（每条可含多个核对输入）；`deck` 至少含最终总览。

```json
{
  "reviews": [
    {
      "stage": "slides",
      "reviewer": "实际模型或工具名称；self-review 或 independent",
      "call_ref": "可定位的宿主工具调用/会话记录引用",
      "inputs": [
        {"path": "renders/r01/slide-1.png", "sha256": "实际文件的SHA256"}
      ],
      "observation": "实际观察到的页面内容、阅读路线和检查结果",
      "decision": "revise",
      "issues": ["P1右下角图例过小：拆成局部放大图再复审"]
    }
  ]
}
```

`decision` 取 `pass`、`revise`、`blocked`。每次修复追加记录，不抹掉失败历史；新版本通过记录的 `issues` 应为空。可接受的轻微风格取舍写入 observation，不用未解决的可读性或事实错误换取通过。旧记录的输入文件也要保留，不能把新图覆盖到同一路径让历史失真。

`bridge.py render` 生成 `render.json`，包含输入文件哈希、逐页图哈希、总览图哈希。生成图片后，应通过宿主图片查看/视觉工具真正打开，不是只把这些路径写进日志。

## 增量与失效规则

内容/图片/布局变化：重新渲染，审阅变更页及受影响邻页。改字体、主题、页码等全局属性：重新渲染整套并审阅所有受影响页。交付时每页必须能对应一条匹配**当前图片哈希**的通过记录，整套结论对应最终总览。

`check_review.py <render.json> <review-log.json>` 只检查五阶段记录是否齐全、输入文件是否变化、最终每页与总览是否有通过记录。它不发送图像、不调用模型、不判断审美、不验证论文内容，也不能证明 call_ref 真实存在。脚本通过只能叫“记录一致性检查通过”，不能叫“视觉模型验收通过”。独立审查 call_ref 属于宿主/人的责任。

## 失败与交付

无图像输入能力 → `blocked_visual`。图片/字体/渲染失败 → 保留失败日志，修复工具或换可用渲染路径。重复修复无改善 → 改表达方式；仍不合格就明确未通过。

最终 `qa-summary.md` 应分别写：事实检查、视觉模型/自审方式、最后审阅版本、工具检查、实测渲染器、目标 PowerPoint 是否实际打开过、未解决问题。任何一项未做就写未做，不使用“所有检查已通过”的概括掩盖缺口。
